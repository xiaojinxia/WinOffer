# 求职记录系统：产品与开发计划

日期：2026-09-21  
状态：本地可用版本已实现。本文保留需求与规划过程，实际实现及验收见 [交付说明](implementation.md)。

## 1. 目标与已确认需求

将求职记录从以表格为主的维护方式，改为以招聘进度为主的查看和更新方式。

- 每条投递记录显示为一条横向进度线，线上各节点代表招聘阶段。
- 默认阶段为：投递简历 → 测评 → AI 面试 → 笔试 → 一面 → 二面 → 三面 → HR 面 → Offer。
- 每个节点可以记录自己的状态，能够表达“一面未通过”和“一面已通过，等待二面”。
- 参考现有飞书记录中的公司、类型、城市、岗位、招聘链接、投递时间、考试或截止时间、结果与薪资信息。
- 第一版仅供本人在自己电脑上使用，不需要跨设备同步。
- 采用本地网页，启动后通过浏览器打开。
- 总览中相同阶段尽量上下对齐，不需要的阶段留空或标为跳过。
- 提供默认流程，每条投递可增删、跳过节点或调整节点顺序。
- 第一版手动录入，不做飞书数据导入或自动同步。
- 第一版只记录时间，不做提醒。

截图用于理解现有数据和展示偏好，不代表每家公司都采用相同流程，也不据此推断某条投递的实际结果。

## 2. 建议的核心界面

### 2.1 投递总览：第一版的主要页面

每条记录分为三个区域：

1. 基本信息：公司、岗位、城市、公司类型。
2. 招聘进度线：节点名称、状态标识、当前节点的关键时间。
3. 当前摘要和快捷操作：例如“一面已通过 · 等待二面安排”，以及更新进度、打开招聘链接。

示意，仅用于解释交互，不代表真实投递：

```text
示例公司 · Java 后端 · 合肥                 一面已通过，等待二面安排
● 投递 ─ ● 测评 ─ ⊘ AI 面 ─ ● 笔试 ─ ● 一面 ─ ○ 二面 ─ ○ 三面 ─ ○ HR 面 ─ ○ Offer
```

- 节点同时使用颜色、图形和文字表示状态，不能只依赖颜色区分。
- 点击节点打开编辑面板，直接修改状态、时间和备注。
- 点击公司或岗位查看完整投递详情和历史。
- 支持按公司/岗位搜索，按公司类型、城市、当前阶段和投递结果筛选。
- 默认按最近更新排序；结束的投递保留历史，可单独筛选。
- 进度表示招聘阶段，不显示容易误解为成功概率的百分比。

对齐规则：

- 默认九个阶段使用统一列宽，固定左侧公司和岗位，横向滚动时仍能识别投递。
- 未设置的标准阶段显示空位；明确不参加的阶段显示“跳过”。两者均不算未通过。
- 自定义节点显示在所属间隔的扩展区，展开后可编辑；原型阶段验证新增加面、四面等情况的可读性。
- 自由调整顺序和全局严格对齐可能冲突。建议顺序冲突的记录显示“自定义流程”，该行按实际顺序展示，不强行放回标准顺序；其他记录继续对齐。
- 展开详情始终展示完整的实际流程，任何节点都不能因为对齐或折叠而无法访问。

### 2.2 时间信息

在节点下显示已经填写的时间，在编辑面板中维护；不设置独立提醒区域。

区分“某时开始的面试”和“某时之前完成的测评”。允许只填日期或完全不填，避免把未知时间强制记成 00:00。第一版不做临期、逾期或系统外通知。

### 2.3 投递详情

- 基本信息、招聘链接和投递日期。
- 完整流程、每个节点的状态、时间、备注。
- 面试地点或会议链接、面试复盘等可选信息。
- Offer 信息与薪资原文。第一版建议保留原始描述，不强制折算年薪。
- 状态变更历史，便于回溯和纠正误操作。

## 3. 关键业务规则

### 3.1 一条记录代表一次具体投递

建议以“公司 + 岗位 + 本次申请”作为业务对象。同一公司可以有多条投递，不能仅以公司名去重。

招聘批次、部门和申请编号可作为选填信息，用于区分同公司同岗位的不同申请。

### 3.2 区分节点状态和整条投递的结果

建议的节点状态：

| 状态 | 含义 | 示例 |
| --- | --- | --- |
| 未开始 | 尚未进入该阶段 | 二面尚未安排 |
| 已安排 | 已收到具体安排 | 一面定于某日 14:00 |
| 进行中 | 正在处理该阶段 | 测评待完成 |
| 待结果 | 已完成动作，但尚无结论 | 一面结束等待反馈 |
| 已通过 | 已明确通过该阶段 | 一面通过 |
| 未通过 | 已明确淘汰 | 一面未通过 |
| 已跳过 | 本次投递不需要该阶段 | 不要求 AI 面试 |

投递简历可显示“已投递，待筛选”；提交简历不等于简历筛选通过。Offer 节点需要适配“已收到 Offer”的表述。

整条投递单独记录结果，建议包括：进行中、已获 Offer、已结束。结束原因可以是未通过、主动放弃、岗位关闭、拒绝 Offer 等；Offer 接受情况单独保留。

核心规则：

- “一面已通过 + 二面未开始”显示为“一面通过，等待二面安排”。
- “一面待结果”显示为“一面结束，等待反馈”，不能自动判断通过。
- “一面未通过”使投递结束，后续节点显示为未进行，不能显示成全部失败。
- 长时间没有反馈不自动判定未通过；截止时间已过也不等于收到拒信。
- 不要求用户补齐每个历史节点才能登记当前进度；缺失结果不能被系统自动改成通过。
- 已结束记录允许纠正或恢复，以应对误操作、补录信息和招聘流程重新开启。
- 当前摘要由节点状态、安排和投递结果生成，避免另外维护一份相互矛盾的“当前状态”。

### 3.3 流程模板与每条投递的流程

已确认提供默认模板，同时允许每条投递增加、删除、跳过和调整节点顺序，例如增加主管沟通或四面。

模板只用于新建投递；修改模板不应悄悄改动已有投递的历史。删除已有内容的节点时，需要提示影响并保留恢复路径。

第一版使用线性流程，不做调剂、并行面试等分支编辑。各记录独立保存自己的节点，标准阶段通过稳定标识对齐，自定义名称不自动判定为同一个标准阶段。

## 4. 第一版范围建议

### 核心功能

- 新建、查看、编辑和结束投递记录。
- 每条投递一条进度线，支持节点状态、时间和备注更新。
- 每条投递自定义流程，包括增删、跳过和调整节点顺序。
- 搜索、筛选，以及按最近更新、投递日期排序。
- 投递详情及状态变更历史。
- 本地数据库保存、备份导出和恢复能力。

### 第一版明确不做

- 飞书导出的 Excel/CSV 导入或自动同步。
- 近期安排提醒、逾期提示、邮件或手机通知。
- 跨设备同步、多用户账户和登录。
- 专门的手机布局、统计报表、自动抓取招聘信息。

### 后续可选

- 飞书数据导入、日历视图和邮件等主动提醒。
- 各阶段转化统计、Offer 对比和面试复盘整理。
- 飞书自动同步、多用户账户、自动解析通知内容。

## 5. 数据结构草案

业务对象以投递记录及其有序节点为核心，不把界面列的位置当作实际招聘顺序。

| 对象 | 主要信息 |
| --- | --- |
| 投递记录 | 公司、岗位、部门、城市、公司类型、招聘链接、申请编号、批次、投递日期、整体结果、结束原因、薪资备注 |
| 流程节点 | 所属投递、标准阶段标识或自定义类型、名称、实际顺序、状态、实际完成时间、备注 |
| 节点时间信息 | 直接保存在节点中：安排时间、截止时间、日期精度、地点或链接；首版无需独立日程模块 |
| 状态历史 | 操作时间、变更对象、原状态、新状态、相关备注 |
| 流程模板 | 名称、有序节点列表；用于创建新的投递流程 |

公司类型、城市和岗位标签沿用用户现有分类习惯。城市可多选，避免丢失现有记录中的多城市信息。

如果后续增加飞书导入，应先预览列映射、重复项和异常值。原“进度”里的多个标签未必表示这些阶段均已通过，不能直接推断为通过；不确定信息保留原文并提示补充。

## 6. 开发顺序与验收

| 阶段 | 工作内容 | 验收目标 |
| --- | --- | --- |
| 1. 确认范围（已完成） | 本地网页、阶段尽量对齐、流程可改、手动录入、只记时间 | 核心范围已有明确决定 |
| 2. 交互原型 | 投递总览、节点编辑、投递详情；使用模拟数据 | 一眼看出当前阶段、结果和下一件事；验证跳过、自定义节点和顺序冲突的展示 |
| 3. 核心闭环 | 新增投递 → 更新节点 → 显示摘要 → 保存 → 重新打开 | 一条真实投递可完整记录，刷新后信息仍在 |
| 4. 效率功能 | 自定义流程、搜索筛选、排序、快捷新建 | 能承载现有数十条投递，减少重复录入 |
| 5. 验证交付 | 备份恢复、异常数据、状态纠正、本机启动和操作说明 | 数据可恢复，关键状态表达准确，日常使用稳定 |

验证重点是业务差异：待结果与已通过、跳过与未通过、主动放弃与被拒绝，以及同公司多次申请。界面验证覆盖约 100 条记录和较长自定义流程；数据验证覆盖重启后保留和备份恢复。

## 7. 建议技术方案

- 前端：原规划为 React + TypeScript；原型获认可后沿用原生 JavaScript 模块，集中实现进度线列表、编辑面板和流程调整，减少本机安装步骤。
- 本地服务：Node.js，为页面提供记录读写和备份恢复接口；仅监听本机回环地址。
- 存储：SQLite，数据保存为本机文件，建议默认位置为项目的 `data/winoffer.sqlite`，由本地服务管理。
- 启动：提供 Windows 启动脚本，启动服务后打开浏览器；首次安装依赖与日常启动分开说明。
- 日常运行：页面资源随程序提供，记录和编辑可离线进行；招聘链接仍在浏览器打开外部网站。
- 备份：导出带版本号的完整 JSON，包含记录、节点和历史。恢复前验证格式并保留当前数据备份，避免恢复失败破坏现有数据。
- 一次节点更新涉及投递结果和历史时，使用数据库事务共同保存；保存失败时界面不应显示已保存。
- 依赖版本和 SQLite 驱动在开始实现时按实际 Node.js 环境确定并锁定，不在规划阶段预设未验证的版本组合。

选型依据：SQLite 官方将本地应用数据存储列为适用场景，适合这个单人、单机的使用范围，参见 [SQLite 适用场景](https://www.sqlite.org/whentouse.html)。具体前后端选型属于实现建议，不是已确认的用户技术偏好。

## 8. 下一阶段的具体验收样例

1. 新建投递只强制填写公司和岗位，生成默认流程，其他信息允许稍后补充。
2. 标记“一面待结果”后，总览显示等待反馈；改为“已通过”后，显示等待下一有效阶段安排。
3. 标记“一面未通过”后，保留此前历史，结束投递，后续节点不被误标为失败。
4. 删除本次无需参与的 AI 面试、增加四面或调整测评/笔试顺序后，实际顺序正确，标准流程仍可对齐比较。
5. 同一公司新增不同岗位或同岗位的第二次申请时，均可独立维护。
6. 关闭浏览器并重启服务后，记录仍在；导出并恢复后，节点顺序、状态、时间和备注完整。
7. 约 100 条记录及较长公司名、岗位名、自定义流程下，仍能识别当前进度并正常编辑。
